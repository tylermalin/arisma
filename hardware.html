EnclaveEdge X1.

A security gateway that gives every machine behind it a hardware identity, with no changes to the machines themselves.

platform / hardware

Insecure on one side. Zero trust on the other.

The X1 sits between a site's machines and the network. It takes in their unauthenticated local traffic and signs it with a key held in a discrete TPM 2.0 chip, then sends it on over mutual TLS. The private key never leaves the chip.

TPM
Discrete TPM 2.0 on its own SPI bus
Operating range

Signed A/B images with automatic rollback

Seven industries, one TPM interface.

Each vertical runs as its own container with its own ingest driver. All of them hand their data to the same TPM interface, so one gateway design covers every site.

The gateway proves custody from the moment it receives a reading. It cannot prove the device upstream was honest.

It refuses to start if anything changed.

Boot is both verified and measured. The SoC boot ROM checks the bootloader's signature (NXP HAB on the i.MX option). Each later stage is hashed into the TPM's PCR registers. The gateway's signing key is sealed to those measurements, so a modified system cannot sign anything, and the root filesystem is checked block by block with dm-verity. A system that fails verification halts before any container runs.

Trusted from the factory to the last update.

The gateway's identity is created inside the chip at manufacture and proven again every time it connects or updates.

  1. 01

    Identity made at the factory

    Each TPM ships with an endorsement key and a certificate from Infineon. At our factory, we create a device identity key and an attestation key inside the TPM, and our certificate authority signs them, tied to that endorsement key. That certificate is the gateway's permanent identity.

  2. 02

    Zero touch provisioning

    Plugged into a WAN, the gateway calls out to the orchestration layer and presents a TPM quote of its boot measurements, which the backend checks. No one configures it by hand.

  3. 03

    Signed updates with rollback

    The root filesystem is atomic and read only. Updates arrive as signed images on an A/B pair. If a new image fails verified boot, the gateway falls back to the last good one.

Every message carries its own proof.

The gateway packages the raw readings, the state of the hardware, and a signature made inside the TPM into one envelope. Change any reading and the digest no longer matches the signature.

gateway_identity
Who is talking. The device identity certificate thumbprint is the gateway's permanent identity, which the backend checks against its fleet.
trust_telemetry
What state the hardware is in. The attestation quote covers the boot measurements, so the backend checks them itself instead of trusting a status string. The sequence counter stops replays.
payload
The readings themselves, with the vertical and the local machine they came from.
cryptographic_proof
The seal. The TPM signs a digest of the payload and trust telemetry. The private key never leaves the chip, and traffic on the SPI bus is encrypted with a TPM session, so a probe on the bus sees nothing useful.

Specifications.

Two compute options share one TPM design, board layout, and software image.

Compute
NXP i.MX8M Nano QuadLite, industrial range −40 to 105 °C, or Raspberry Pi Compute Module 4, industrial variant, −20 to 85 °C
TPM
Infineon OPTIGA™ TPM SLB 9670, discrete, on a dedicated SPI bus
TPM bus
SPI with encrypted TPM sessions (parameter encryption)
TPM certification
The SLB 9670 is certified to Common Criteria EAL4+
Memory
2 GB LPDDR4
Storage
16 GB eMMC 5.1 in SLC mode, for write endurance and resistance to corruption
Local OT network
1× RJ45 Gigabit Ethernet, isolated, with routing and forwarding disabled
WAN
1× RJ45 10/100 Ethernet, or a Nano SIM slot for LTE Cat-M1 failover
Expansion
2× isolated CAN FD, 1× RS-485 (Modbus), 1× USB 2.0 host
Operating system
Hardened, read only root filesystem on Yocto Project Linux or Ubuntu Core
Boot
Verified boot, measured into TPM PCRs; signing key sealed to those measurements
Tamper
Case switch loop wired to the SoC's secure tamper input; a trip wipes session keys and is logged
Containers
LXC or Docker with namespace, cgroup, and seccomp isolation
SPI interconnect referencePin mapping between the host and the TPM, for hardware engineers

Standard four wire SPI, plus an interrupt for asynchronous alerts and a reset line so the host can power cycle the TPM. Package pin numbers are in the Infineon SLB 9670 datasheet. The tamper loop is wired to the SoC's secure tamper input, not to the TPM. Header pin numbers in the CM4 column apply to the CM4 IO board; on a custom carrier, map by GPIO number.

Device tree overlay, Raspberry Pi CM4

Reference only. Validate against your carrier board and the upstream Raspberry Pi SLB 9670 overlay before use. Binds the SLB 9670 to SPI0 chip select 0 through the kernel's TPM TIS SPI driver, with reset on GPIO 25 and the interrupt on GPIO 24. Saved as tpm-slb9670-overlay.dts.

dtc -@ -I dts -O dtb -o tpm-slb9670.dtbo tpm-slb9670-overlay.dts
/dts-v1/;
/plugin/;

/ {
    fragment@0 {
        target = <&spi0>;
        __overlay__ {
            #address-cells = <1>;
            #size-cells = <0>;
            status = "okay";

            spidev@0 { status = "disabled"; };

            tpm_enclave: slb9670@0 {
                compatible = "infineon,slb9670", "tcg,tpm_tis-spi";
                reg = <0>;
                spi-max-frequency = <32000000>;
                status = "okay";
                gpios = <&gpio 25 1>;
                interrupt-parent = <&gpio>;
                interrupts = <24 1>;
            };
        };
    };
};
