Chapter 01

Why machines need new rails.

Card networks were designed around a person at a checkout. They price in credit risk, settle in batches, and charge a fixed fee per transaction that makes sense on a $40 purchase. A drone buying $0.14 of charge, a robot paid per pick, or a sensor selling a single reading breaks every one of those assumptions.

Machines need three things instead: authority they can prove with no person present, payments that confirm in seconds and reach finality soon after, and behavior that is bounded and checkable. The rest of this paper builds those three properties, one layer at a time.

Chapter 02

Trust model: authority without exposing keys.

An agent needs to act on its owner's behalf without holding the owner's master key. Arisma issues it a mandate: a narrow, expiring grant of authority on a smart account. The account uses ERC-7702 to point at Arisma's permission module, and the mandate's key lives in hardware. For agents in a data center, that is an AMD SEV-SNP or Intel TDX confidential VM. For physical machines, it is the TPM in an EnclaveEdge X1 gateway.

Before a mandate is issued, Arisma checks the hardware through remote attestation: a confidential VM's attestation report, or the X1's TPM quote. The owner key stays with the owner. What the machine holds is a key that can do a few named things, for a few minutes, and nothing else.

Chapter 03

Settlement topology: netted, deterministic, checkable.

Every interaction follows the same path: mandate, evidence, settle, release, receipt. The actor changes, a drone, a robot arm, a vehicle, a sensor, but the path does not.

Payments settle in USDC on Base, a Layer 2. A single payment, like a drone charge, confirms in about 1.4 seconds. Per-action payments, like a pick or a reading, are netted under the mandate and settled in batches, so each action still carries its own price and its own receipt. Receipts are deterministic: the same inputs always produce the same receipt, so anyone can check one later.

A receipt being deterministic makes it checkable. Finality is a separate question: it is the point after which the chain cannot reverse the payment. On Base that point is Ethereum finalization, not the first confirmation.

Key idea

Determinism turns a receipt into evidence. Anyone holding the inputs can recompute it and get the same answer.

Chapter 04

Attestation: proving what happened in the physical world.

Paying a machine is only safe if you can trust what it reports. Before value or machinery is released, Arisma checks three things: the key that signed is held in attested hardware, the policy holds, and the physical telemetry carries a valid signature from a known gateway, and media captures carry a C2PA manifest.

Policy proofs, which would let the gate check a rule without seeing the readings behind it, are on the roadmap. On testnet today, the gate checks signed readings against the policy directly.

For high stakes actions, a person holds the final gate. Releasing a payload or starting heavy machinery waits for a human decision, however many automated checks have passed.

What a proof cannot do

A proof is only as good as its inputs. If a sensor upstream of the gateway is spoofed, the gateway signs spoofed data. Arisma proves custody from the gateway onward and makes any later change detectable. For readings that move money, pair the gateway with sealed wiring, cross-sensor checks, or a secure element on the sensor.

Key idea

A gateway signature proves custody from the gateway onward. C2PA ties a media capture to the device that recorded it.

Chapter 05

Economic security: bounding the cost of misbehavior.

No system can promise a key will never leak or a machine will never misreport. What it can do is make the worst case small and known in advance. A mandate's worst case comes from numbers you choose when you issue it: what each action costs, how fast actions can happen, how long the key lives, and an optional spending cap.

The full specification adds incentive and penalty parameters for machine actors. This chapter covers the part you control directly: the bound.

Chapter 06

Threat model.

No mandate removes risk. Each threat below has a named limit and a named residual.

ThreatWhat limits itWhat remains
A mandate key leaksScope, cap, rate, expiry, max price per actionLoss up to the Chapter 5 bound
The owner key leaksHardware wallet; delay on mandate changesFull account. This is the owner's key to protect.
A sensor upstream of the gateway is spoofedSealed wiring, cross-sensor plausibility checks, per-sensor secure elements for high-value readingsThe gateway signs what it receives
A gateway is physically attackedTamper loop, signing key sealed to boot measurements, TPM quote on every connect, remote revocationAn attacker with lab equipment and time
A payment is reversed before finalityHigh-value releases wait for Ethereum finalizationShort window between confirmation and finality
A message is replayedSequence counter, nonce, expiryNone known
Arisma's verifier is wrong or compromisedReceipts and quotes are recomputable by anyone; verifier code publishedOperator trust until verification is independent
Key idea

A mandate bounds what an agent can lose. It does not protect the owner key, and a signature does not make an upstream sensor honest. Name the residual, then decide who carries it.

Summary

What you covered.

  • 01New rails. Fixed fees and a cardholder make small machine payments impossible on card networks.
  • 02Trust. Mandates carry narrow, expiring authority, signed by a key held in hardware. The owner key stays with the owner.
  • 03Settlement. One path for every actor. Single payments confirm in about 1.4s on Base, small ones are netted, and deterministic receipts are evidence.

Reference

Glossary.

Mandate
A scoped, expiring permission to spend.
Session key
A narrow, expiring key an agent uses instead of its owner's master key. It can perform only the actions in its scope, until it expires.
ERC-7702
An Ethereum standard that lets an ordinary account point to smart contract code. Arisma uses it to give an account a permission module, which issues mandates.
Hardware enclave
An isolated region of a processor, also called a trusted execution environment, whose memory the host operating system cannot read. Keys created inside stay inside.
AMD SEV-SNP
AMD's confidential computing technology. It encrypts a virtual machine's memory and protects it from the host.
Intel TDX
Intel Trust Domain Extensions, which isolate a virtual machine from the host and the hypervisor.
TPM
A chip that stores keys and records what software booted.
P-256
The signature curve TPMs and passkeys use.
RIP-7212
A precompile that lets L2 contracts verify P-256 signatures cheaply.
Remote attestation
A signed report from the hardware stating exactly what code is running, so a remote party can decide whether to trust it.
Zero knowledge proof
A proof that a statement is true which reveals nothing beyond the fact that it is true.
C2PA
An open standard for attaching tamper-evident provenance to images, video, audio, and documents. Arisma uses it for media captures, such as drone inspection footage.
Finality
The point after which a settlement cannot be reversed.
USDC
A dollar stablecoin issued by Circle, redeemable one for one in US dollars.
Layer 2
A network that executes transactions away from a base blockchain and settles them back to it, for lower cost and faster confirmation.
Netting
Combining many small payments into one settlement.
Deterministic receipts
The same inputs always produce the same output, so anyone can recompute and check a receipt.
