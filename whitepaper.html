Chapter 01

Why machines need new rails.

Card networks were designed around a person at a checkout. They price in credit risk, settle in batches, and charge a fixed fee per transaction that makes sense on a $40 purchase. A drone buying $0.14 of charge, a robot paid per pick, or a sensor selling a single reading breaks every one of those assumptions.

Machines need three things instead: authority they can prove with no person present, settlement that reaches finality in seconds, and behavior that is bounded and checkable. The rest of this paper builds those three properties, one layer at a time.

Chapter 02

Trust model: authority without exposing keys.

An agent needs to act on its owner's behalf without holding the owner's master key. Arisma issues it a session key: a narrow, expiring grant of authority, defined with ERC-7702 and signed inside a hardware enclave such as AMD SEV-SNP or Intel TDX.

The enclave proves what code it runs through remote attestation before any session is trusted. The master key never leaves it. What leaves is a key that can do a few named things, for a few minutes, and nothing else.

Chapter 03

Settlement topology: deterministic, subsecond, metered.

Every interaction follows the same path: delegate, attest, settle, verify, anchor receipt. The actor changes, a drone, a robot arm, a vehicle, a sensor, but the path does not.

Microsettlements clear on Layer 2 stablecoin rails in USDC with subsecond finality, metered to the fraction of a cent so a single charge, pick, or reading can carry its own payment. Clearing is deterministic: the same inputs always produce the same receipt, so anyone can check a receipt later.

Chapter 04

Attestation: proving what happened in the physical world.

Paying a machine is only safe if you can trust what it reports. Before value or machinery is released, Arisma checks three things: the enclave runs the expected code, the policy holds as shown by a zero knowledge proof, and the physical telemetry matches its C2PA provenance hash.

For high stakes actions, a person holds the final gate. Releasing a payload or starting heavy machinery waits for a human decision, however many automated checks have passed.

Chapter 05

Economic security: bounding the cost of misbehavior.

No system can promise a key will never leak or a machine will never misreport. What it can do is make the worst case small and known in advance. A session key's worst case comes from numbers you choose when you issue it: what each action costs, how fast actions can happen, how long the key lives, and an optional spending cap.

The full specification adds incentive and penalty parameters for machine actors. This chapter covers the part you control directly: the bound.

Reference

Glossary.

Session key
A narrow, expiring key an agent uses instead of its owner's master key. It can perform only the actions in its scope, until it expires.
ERC-7702
An Ethereum standard that lets an ordinary account delegate to contract code. Arisma uses it to define scoped session keys.
Hardware enclave
An isolated region of a processor, also called a trusted execution environment, whose memory the host operating system cannot read. Keys created inside stay inside.
AMD SEV-SNP
AMD's confidential computing technology. It encrypts a virtual machine's memory and protects it from the host.
Intel TDX
Intel Trust Domain Extensions, which isolate a virtual machine from the host and the hypervisor.
Remote attestation
A signed report from the hardware stating exactly what code is running, so a remote party can decide whether to trust it.
Zero knowledge proof
A proof that a statement is true which reveals nothing beyond the fact that it is true.
C2PA
An open standard from the Coalition for Content Provenance and Authenticity for attaching tamper evident provenance to media and data.
Finality
The point after which a settlement cannot be reversed.
USDC
A dollar stablecoin issued by Circle, redeemable one for one in US dollars.
Layer 2
A network that executes transactions away from a base blockchain and settles them back to it, for lower cost and faster confirmation.
Deterministic clearing
The same inputs always produce the same output, so anyone can recompute and check a receipt.
